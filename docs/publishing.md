# Публикация новой версии или нового скрипта

## Правила

- Основной файл имеет постоянное имя без версии и без суффикса копии; расширение соответствует исходному языку.
- В первых 10 строках — `# SCRIPT_VERSION: V1.01` для Python или `// SCRIPT_VERSION: V1.01` для C#; в коде — строковая константа `SCRIPT_VERSION` той же версии.
- Последовательность проекта: V1, V1.01, V1.02, …, V1.09, V1.10. Изменение исходника требует следующей редакции; изменение основной версии определяется сопровождающим проекта.
- Сохраняйте сведения об авторстве и постоянные имена рабочих файлов. Название и описание в каталоге задаются полями `name` и `description`.
- `main`, корневой `manifest.json` и пути опубликованных файлов являются постоянными адресами обновлений.
- В таблице README и поле `description` manifest пишите короткое назначение, без истории редакций и формулировок «на основе версии…». Известные ограничения должны оставаться видимыми.
- Для каждого журнала ведите руководство в `docs/`: все пользовательские функции, запуск, настройки, создаваемые или изменяемые файлы и ограничения. В строке README должна быть ссылка «Все функции».
- При каждом выпуске обязательно обновляйте описание на GitHub: в начале руководства скрипта размещайте раздел «Изменения последней версии» с номером, датой и конкретными исправлениями или новыми возможностями. Обновляйте этот раздел даже при исправлении ошибки без изменения порядка работы. Указывайте фактические проверки и существенные ограничения.
- В README показывайте краткое описание самого свежего обновления со ссылкой на этот раздел. Предыдущие записи сохраняйте в CHANGELOG, а раздел последней версии заменяйте актуальным. Обновление исходника, manifest и описаний публикуйте вместе.
- Документация должна быть понятна при первом знакомстве с проектом: без ссылок на личную переписку, внутренний состав предыдущих комплектов и просьб прислать результат в чат. Подробные описания всех скриптов находятся в их руководствах; README содержит общий каталог и установку.

## Новый журнал

1. Поместите проверенный исходник в `scripts/`. Для INI добавьте нейтральный `config/<имя>.example.ini`; личный рабочий INI в Git не копируйте.
2. Добавьте запись в `manifest.json`: `id` (имя без расширения), `name`, `file`, `version`, `path`, `sha256`, `description`. Если нужен INI, добавьте `config` с `path`, `file`, `location=script`, `sha256`.
3. Для начальной записи SHA-256 можно временно заполнить 64 нулями, затем выполнить команды ниже. Нули публиковать нельзя.
4. Добавьте руководство в `docs/`, ссылку в README и запись CHANGELOG. Проверьте изменённый журнал в целевой NX.

```console
python tools/manifest.py --write
python tools/manifest.py --check
python -m unittest discover -s tests -v
```

`--write` синхронизирует внутренние версии и SHA-256, но не назначает версии и не меняет исходники. `--check` ничего не переписывает. Инструмент также проверяет шапки, константы, Python-синтаксис, примеры INI и отсутствие записей в пустом реестре.

Закоммитьте исходники, примеры и manifest **вместе**. После публикации следующая проверка апдейтера покажет новый журнал без изменения самого апдейтера. Пользователь выбирает его установку; кнопка NX при этом не создаётся.

## Новая редакция существующего журнала

Обновите исходник под тем же именем, согласованно измените обе внутренние версии, выполните проверки и опишите изменение в CHANGELOG. Обязательно обновите раздел «Изменения последней версии» в руководстве скрипта и краткое описание свежего обновления в README. Остальные разделы руководства приведите в соответствие с текущими функциями и порядком работы. Правки только документации и описаний не меняют версию исходника. INI пользователя не обновляется автоматически. Новые настройки должны иметь безопасные значения по умолчанию или отдельную инструкцию переноса; отсутствие ключа не должно приводить к потере пользовательских данных.

Для изменения апдейтера используйте его отдельную редакцию. `min_updater_version` повышайте только если остальной каталог действительно требует новой версии. Изменение несовместимой схемы потребует ручного перехода для старых клиентов.

## Перед коммитом

Проверьте `git diff --cached`: никаких реальных INI, сетевых путей предприятия, паролей, ключей, локальных моделей, пользовательских XLSX, шрифтов, логов и временных файлов. `.gitignore` помогает избежать случайного добавления, но не очищает ранее отслеживаемые файлы или историю Git.

Не публикуйте файл из рабочей папки со служебным `NX_UPDATER_INSTALLED_V1`: используйте чистый исходник. Собственные функциональные изменения сначала перенесите в него и назначьте новую редакцию. Для сторонних ресурсов укажите происхождение и разрешённые условия распространения.

Тесты GitHub Actions проверяют переносимую часть апдейтера на Windows и Linux. На Windows дополнительно проверяются изображение и управление настоящим TreeView постпроцессора. Проверка окон журналов и поведения NXOpen в целом остаётся проверкой в NX 2506.8100 / Designcenter 2606 Build 4002. Результат CI не расширяет список совместимости.
